# LangChain RAG Assessment

## Task 1 — Ingestion

### Objective

The goal of this task is to load, clean, and chunk a PDF containing at least 50 pages, while also recording measurable chunk statistics.

For this task, I used a PDF book containing **136 pages**.

### Implementation

The ingestion pipeline is implemented in:

```text
ingestion/ingestion.py
```

The pipeline performs the following steps:

1. Loads the PDF using `PyPDFLoader`.
2. Checks that the document contains at least 50 pages.
3. Cleans extracted text by removing unnecessary whitespace and line breaks.
4. Splits the pages into smaller chunks using `RecursiveCharacterTextSplitter`.
5. Adds a unique `chunk_id` to every generated chunk.
6. Preserves metadata such as source and page number.
7. Calculates chunk statistics including:

   * Total pages loaded
   * Total chunks created
   * Average chunk size
   * Smallest chunk size
   * Largest chunk size

### Chunking Configuration

```python
chunk_size = 900
chunk_overlap = 120
```

A chunk overlap is used so that important information near chunk boundaries is not completely separated between neighbouring chunks.

### Run the Ingestion Pipeline

```bash
uv run python -m ingestion.ingestion
```

### Save the Output

```bash
uv run python -m ingestion.ingestion > outputs/ingestion_output.txt
```

### Metadata

Each chunk retains document metadata and also receives a unique `chunk_id`.

This metadata will later be used during indexing and citation generation.

### Testing

Automated tests are included in:

```text
tests/test_ingestion.py
```

Run the tests using:

```bash
uv run pytest tests/test_ingestion.py -v
```

Save the test output using:

```bash

```

### Task 1 Result

Task 1 successfully demonstrates PDF ingestion, text cleaning, chunking, metadata preservation, validation of the minimum page requirement, and recorded chunk statistics.

## Task 2 — Index

### Objective

The goal of this task is to convert the document chunks created during ingestion into embeddings and store them in a vector store while preserving metadata required for retrieval and citations.

The index stores metadata including:

* `source`
* `page`
* `chunk_id`

### Implementation

The indexing pipeline is implemented in:

```text
index/index.py
```

The pipeline performs the following steps:

1. Reuses the chunks generated by the Task 1 ingestion pipeline.
2. Loads the embedding configuration from environment variables.
3. Converts each text chunk into an embedding vector.
4. Stores the vectors using FAISS.
5. Preserves the metadata associated with each chunk.
6. Saves the FAISS index locally so it can be reused during retrieval.

### Embeddings

Embeddings are created using `OpenAIEmbeddings` configured through the OpenRouter API.

The API key, base URL, and embedding model are read from environment variables rather than being stored directly in the source code.

A timeout and capped retries are configured for the external embedding request.

### Vector Store

FAISS is used as the vector store. Each document chunk is converted into a vector and stored together with its associated document metadata.

The completed vector store is saved locally under:

```text
vector_store/
```

This allows later tasks to load the existing index instead of regenerating all embeddings.

### Run the Indexing Pipeline

```bash
uv run python -m index.index
```

### Save the Output

```bash
uv run python -m index.index > outputs/index_output.txt
```

### Metadata Preservation

The indexed documents preserve their original metadata and the `chunk_id` added during ingestion.

Additional PDF metadata such as author, title, total pages, and page label is also preserved.

The `source` and `page` metadata will be used later to produce citations for grounded RAG answers.

### Testing

Automated tests are included in:

```text
tests/test_index.py
```

The success test verifies that documents can be converted into a FAISS index and that the expected number of vectors are stored.

The failure test verifies that attempting to create an index without document chunks raises a `ValueError`.

Fake embeddings are used only inside the automated tests so that unit tests remain deterministic and do not require external API calls. The actual indexing pipeline uses real embeddings.

### Run the Tests

```bash
uv run pytest tests/test_index.py -v
```

### Save Test Evidence

```bash
uv run pytest tests/test_index.py -v > outputs/index_test_output.txt
```

### Task 2 Result

Task 2 successfully converts the **254 chunks from 136 PDF pages into embedding vectors and stores all 254 vectors in FAISS**.

The required `source`, `page`, and `chunk_id` metadata is preserved, and the vector index is persisted locally for use in the retrieval and grounded-answer stages.

## Task 3 — Grounded Answers

### Objective

The goal of this task is to answer user questions using only the context retrieved from the vector store and include inline citations containing the source and page number.

### Implementation

The grounded RAG pipeline is implemented in:

```text
grounded_answers/grounded_answers.py
```

The pipeline performs the following steps:

1. Loads the FAISS index created in Task 2.
2. Converts the user question into an embedding using the same embedding model.
3. Retrieves the top 4 most relevant chunks from the vector store.
4. Formats the retrieved chunks together with source and page information.
5. Sends only the retrieved context and question to the chat model.
6. Instructs the model to answer only from the supplied context.
7. Requires inline citations in the format `[source pN]`.

### Retrieval

The retrieval step uses FAISS similarity search:

```python
documents = store.similarity_search(
    question,
    k=TOP_K,
)
```

The value of `TOP_K` is set to:

```text
4
```

This means that only the four most relevant chunks are selected for answering the question instead of sending the complete document to the model.

### Context Formatting

Retrieved documents are formatted with their citation metadata.

The context includes both the text and its original source information so that the model can generate grounded citations.

### Page Metadata

The PDF loader provides both an internal page number and a page label.

Where available, `page_label` is used for citations because it corresponds more closely to the visible PDF page number.

If `page_label` is not available, the normal `page` metadata is used as a fallback.

### Grounding Prompt

The model is explicitly instructed to:

* Use only the retrieved context.
* Avoid outside knowledge.
* Add inline citations.
* Return `insufficient evidence` if the provided context is not enough.

This helps reduce unsupported answers and keeps the response tied to retrieved evidence.

### Run the Grounded Answer Pipeline

```bash
uv run python -m grounded_answers.grounded_answers
```

### Save the Output

The failure test verifies that an empty question is rejected with a `ValueError`.

The tests use a small fake retrieval store so that unit testing remains deterministic and does not require an external API call.

Task 3 successfully demonstrates the retrieval and generation stages of RAG. Relevant chunks are retrieved from the FAISS index, passed as context to the model, and used to generate answers that include inline source and page citations.
